# 블로그 확장과 design-refactor 통합 배포 설계

## 1. 목표

검증이 끝난 블로그 31편 릴리스와 `feat/design-refactor` 작업 폴더의 아직 유효한 변경을 최신 `master` 위에서 안전하게 정리해 한 번의 정상 PR 흐름으로 배포한다. 이미 `master`에 반영된 기능은 다시 적용하지 않고, 다른 작업의 문서·산출물은 원래 폴더에 보존한다.

## 2. 확인된 현재 상태

- 로컬 `master`는 `97c07b1`이며 `origin/master`보다 블로그 릴리스 12개 커밋 앞에 있다.
- 블로그 릴리스는 31편, 대표 이미지 31개, 전체 자산 79개를 포함한다.
- `feat/design-refactor`의 고유 기능 커밋 중 랜딩 고해상도 화면, 한눈표 시드 마커 제거, 첫 로그인 6단계 안내는 다른 커밋으로 이미 `master`에 반영됐다.
- 랜딩 헤더 단순화와 Free/Plus/Super 3단 요금제도 현재 `master`에 동일한 사용자 동작으로 존재한다.
- 과거 브랜치를 그대로 병합하면 최신 269개 커밋과 충돌하거나 오래된 `AGENTS.md`, `README.md`, 화면 코드를 되살릴 수 있다.
- 원래 작업 폴더의 전략 HTML, DOCX, XLSX, 과거 계획서, `outputs/`는 이번 제품 배포와 별도인 사용자 자료다.

## 3. 통합 원칙

### 3.1 이미 반영된 기능

다음 변경은 현재 `master`의 구현과 테스트를 권위로 삼고 다시 커밋하지 않는다.

- 랜딩 헤더의 `블로그`, `로그인`, `무료로 시작하기` 구성
- Free/Plus/Super 3단 요금제와 Plus의 Manager 역할 안내
- 첫 로그인 6단계 안내
- 랜딩 제품 화면 5개와 한눈표 시드 마커 제거

이 항목은 현재 구현의 테스트와 브라우저 화면을 재검증하되, 과거 커밋을 cherry-pick하거나 과거 파일 전체를 덮어쓰지 않는다.

### 3.2 아직 이식할 게시판 운영 변경

최신 `master`의 `seed_boards` 멱등성과 관리자 편집 보존 규칙을 유지하면서 아래만 이식한다.

- 기존 개인정보 FAQ가 배포 기본 문구 그대로인 경우에만 더 정확한 계정별 조회 범위, 외부 분석 전 신원정보 가림, 선택 자료 공유 설명으로 갱신한다. 기능 경로에 따라 달라지는 원본 보관 방식은 일괄 약속하지 않는다.
- 스캔 PDF와 휴대폰 사진 PDF, 검토 표시, 원문 대조·수정·확정, 동시 업로드 분리, 고객 동의 순서는 모두 `INSURANCE_REVIEW_GATE_ENABLED`가 `True`인 실행에서만 시드 후보가 된다. 현재 운영 기본값 `False`에서는 생성하지 않는다. 게이트가 닫힌 기존 경로는 스캔·이미지 PDF를 지원하지 않으므로 상시 FAQ로 약속하지 않는다.
- 기존 Manager 공지·FAQ와 관리자 수정 보존 테스트는 삭제하지 않고 새 테스트를 추가한다.
- `cleanup_demo_boards`는 `[DEMO]`로 시작하는 공지와 FAQ만 대상으로 하며 기본 실행은 dry-run이다. `--apply`는 수동 운영 명령으로만 제공하고 Render 시작 명령에는 넣지 않는다.

### 3.3 제외·보존 범위

다음 파일은 삭제하거나 배포 커밋에 포함하지 않는다.

- `inpa_fe/components/__tests__/sales-marketing-execution-html.test.tsx`
- `outputs/` 아래 미리보기, Node 의존성, XLSX

## 4. 커밋 구조

기존 블로그 12개 커밋은 이미 단계별 리뷰와 회귀 검증에 사용된 이력이므로 재작성하지 않는다. 새 변경은 다음 단위로만 추가한다.

1. `docs(배포): 블로그와 디자인 통합 설계`
2. `docs(배포): 블로그와 디자인 통합 계획`
3. `feat(게시판): 기능 상태에 맞춘 안내 보강`
4. `chore(게시판): 데모 공지 정리 명령 추가`
5. `docs(개발): Rosetta 테스트 실패 기록`
6. 운영 배포 성공 뒤 `docs(배포): 블로그와 디자인 통합 기록`

각 커밋은 지정 파일만 명시적으로 stage한다. `git add -A`와 사용자 작업 폴더의 미추적 파일 stage는 금지한다.

## 5. 검증 설계

### 5.1 게시판

- 기능 게이트 `False`: 스캔 PDF를 포함한 공개 전 보험 검토 안내 행이 생성되지 않는다.
- 기능 게이트 `True`: 검토 안내가 한 번만 생성되고 재실행해도 중복되지 않는다.
- 기존 개인정보 FAQ가 공식 과거 문구와 정확히 같을 때만 갱신된다.
- 관리자가 수정한 개인정보·Manager 공지·FAQ는 재실행 뒤 그대로 유지된다.
- `cleanup_demo_boards` 기본 실행은 행을 삭제하지 않는다.
- `--apply`는 `[DEMO]` 공지와 FAQ만 삭제하고 일반 공지, 게시글, 댓글, 고객은 건드리지 않는다.

### 5.2 블로그와 프론트엔드

- 블로그 릴리스 테스트, 공개 예약 시각 테스트, 31편 중복 검사, 31/31/79 자산 검사를 다시 실행한다.
- 전체 Vitest와 Next 운영 빌드를 실행한다.
- 랜딩 데스크톱·모바일에서 헤더, 요금제, CTA, 가로 넘침, 콘솔 오류를 확인한다.
- 카피 검사에서 쉬운 말, 금지 표현, em dash 위반이 0건이어야 한다.

### 5.3 백엔드와 데이터

- Django check와 전체 `manage.py test inpa`를 실행한다.
- `refresh_blog_content` dry-run이 31편, 기존 25편, 신규 6편, 수정 대상 6편을 보고하고 DB 지문을 바꾸지 않아야 한다.
- 배포 전 마이그레이션 순서와 롤백 명령을 확인한다.

## 6. 게시와 배포

1. `git fetch origin` 후 `origin/master`에 새 변경이 있으면 최신 변경을 보존해 통합한다.
2. `codex/blog-design-release`만 푸시하고 `master` 대상 초안 PR을 만든다.
3. GitHub Actions와 Vercel 프리뷰가 모두 통과해야 한다.
4. 프리뷰에서 블로그 목록, 변경된 글 12편, 랜딩 데스크톱·모바일을 확인한다.
5. PM에게 프리뷰와 검증 결과를 공유하고 운영 병합 확인을 받는다.
6. PR을 정상 병합해 Vercel과 Render 자동 배포를 시작한다.
7. 운영 URL, Render health, v3 릴리스 적용, 미래 글 404, sitemap 비노출, 오류 로그 5분을 확인한다.

## 7. 롤백

- 코드·화면: 배포 PR의 merge commit을 revert하는 새 PR을 사용한다.
- 블로그 DB: `python manage.py refresh_blog_content --restore-from-marker --confirm-version 2026-08-internal-organic-v3`로 v3 직전 snapshot을 복원한다.
- 공개 전 보험 검토 안내는 기능 게이트가 닫힌 운영에서는 생성되지 않는다. 잘못 생성된 행을 자동 삭제하지 않고 Django admin에서 상태를 확인한 뒤 별도 복구한다.
- `cleanup_demo_boards --apply`는 이번 자동 배포에서 실행하지 않으므로 데이터 삭제 롤백은 발생하지 않는다.

## 8. 완료 기준

- 승인 범위의 모든 변경이 추적되고 커밋 단위가 분리돼 있다.
- 사용자 작업 폴더의 제외 파일은 원본 그대로 남아 있다.
- 전체 백엔드·프론트엔드·블로그·카피·빌드 검사가 통과한다.
- 독립 리뷰에서 Critical과 Important가 0건이다.
- PR, CI, 프리뷰, 운영 배포, v3 데이터 적용, 운영 스모크가 모두 확인된다.
- 운영 성공 후 `README.md`와 `AGENTS.md`에 실제 배포 증거가 기록된다.
