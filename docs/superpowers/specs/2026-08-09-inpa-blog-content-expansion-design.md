# 인파 블로그 신규 5편과 발행일 재배치 설계

> 작성일: 2026-08-09
> 상태: PM 방향 승인, 구현 계획 작성 전
> 대상: 기존 원고 20편의 발행일 재배치, 신규 원고 5편과 이미지 추가
> 공개 작성자: 전편 `인파 담당자`

## 1. 목표

기존 보장분석과 상담 준비 중심의 글에 업무 운영, 개인 브랜드, 영업 복기, 장기 고객관리, 팀장 코칭 관점을 더한다. 기존 20편은 2026년 7월 1일부터 8월 7일까지 실제 영업일에 자연스럽게 나누고, 신규 5편은 8월 10일부터 순차 공개한다.

성공 조건은 다음과 같다.

1. 기존 20편의 제목, 본문, 태그, 이미지, 관리자 수정 내용은 보존하고 발행 시각만 바뀐다.
2. 기존 20편의 편집 일정은 주말과 2026년 7월 17일 제헌절을 제외한다.
3. 같은 날 2편인 경우 오전과 오후로 나누며 모든 시각은 서로 다르다.
4. 법률 검토 대상 3편은 내부 일정만 기록하고 `published_at=null`, `is_published=false`를 유지한다.
5. 신규 5편은 각각 고유한 대표 이미지, 설명 도식, 실제 인파 화면을 가진다.
6. 신규 글은 예약 시각 전까지 목록, 상세, 관련 글, 사이트맵에 나타나지 않는다.
7. 공개 저자는 API, 화면, 검색 구조화 데이터에서 모두 `인파 담당자`로 유지한다.
8. 특정 상품 추천, 과장된 성과, 가짜 후기, 실제 고객 정보, 생성형 티가 나는 시각 표현을 넣지 않는다.

## 2. 접근안과 결정

| 접근 | 장점 | 단점 | 결정 |
|---|---|---|---|
| A. 글 5편과 대표 이미지 5장만 추가 | 변경 범위가 작다 | 기존 글과 체감 차이가 작고 이해를 돕는 자료가 부족하다 | 제외 |

## 3. 신규 콘텐츠 5편

신규 글은 1,800자에서 2,600자 범위를 기본으로 한다. 분량보다 사실 밀도와 저장 가능한 결과물을 우선한다. 구성은 `핵심 답 -> 실제 상황 -> 단계별 방법 -> 합성 예시 -> 놓치기 쉬운 점 -> 저장용 체크리스트 -> 관련 기능` 순서를 따른다.

| # | 카테고리 | 제목 | slug | 독자가 가져가는 결과물 |
|---|---|---|---|---|
| 21 | 고객 늘리기 | 보험설계사 주간 계획표, 고객 단계별로 다음 행동 정하기 | `보험설계사-주간-계획표-고객-단계별-다음-행동` | 한 주 동안 고객 단계를 고르게 움직이는 점검표 |
| 22 | 고객 늘리기 | 보험설계사 소개 카드, 고객이 연락 전에 확인할 5가지 | `보험설계사-소개-카드-고객-확인사항` | 과장 없이 소속, 역할, 상담 방식, 연락 방법을 정리하는 소개 문장 |
| 23 | 설계사 이야기 | 보험설계사 월말 복기, 결과보다 먼저 볼 5개 숫자 | `보험설계사-월말-복기-영업-숫자` | 신규 고객, 연락, 미팅, 청약, 다음 행동을 함께 보는 월말 점검표 |
| 24 | 고객 늘리기 | 고객 생일·만기·갱신 일정을 연간 관리표로 정리하는 법 | `보험설계사-고객-연간-일정-관리법` | 필요한 날짜만 남기고 12개월 접점을 계획하는 연간 관리표 |
| 25 | 설계사 이야기 | 보험설계사 팀장 1:1, 실적 확인 뒤 물어볼 6가지 | `보험설계사-팀장-일대일-질문` | 결과만 재촉하지 않고 다음 행동과 지원을 정하는 면담 질문표 |

### 글별 사실 경계

- 21: 특정 활동량이 성공을 보장한다고 쓰지 않는다. 고객 단계별 다음 행동을 고르게 배치하는 운영법으로 한정한다.
- 22: 자격, 경력, 실적은 확인된 사실만 쓰며 최고, 유일, 보장 같은 표현을 예시에서도 사용하지 않는다.
- 23: DB, TA, FA, 청약은 설계사 현장 용어를 처음 한 번 풀어 쓴다. 현재 분포를 장기 전환율처럼 표현하지 않는다.
- 24: 생일 전체 날짜와 계약 일정은 필요한 목적과 범위만 저장한다. 민감한 가족 정보나 병력을 일정 제목에 쓰지 않는다.
- 25: 가상의 팀 사례임을 밝힌다. 개인 고객 정보가 아닌 활동 단계와 지원 요청만 다룬다.

모든 사실 출처는 원고 메타데이터에 공식 URL과 `checked_at=2026-08-09`를 남긴다. 우선 출처는 개인정보보호위원회, 금융감독원·보험협회, 보험연구원, 인파의 공개 기능 설명이다. 검색 결과나 다른 사업자의 마케팅 문구는 사실 근거로 사용하지 않는다.

## 4. 이미지 설계

신규 자산은 총 15개를 목표로 한다.

- 대표 이미지 5장: 1600×900 WebP, 글자와 로고가 없는 편집 사진형 장면
- 설명 도식 5장: 1600×900 WebP, 인파 디자인 토큰 기반 직접 제작
- 실제 화면 5장: 촬영용 합성 계정과 가상 데이터로 캡처

| 글 | 대표 이미지 | 설명 도식 | 실제 화면 |
|---|---|---|---|
| 주간 계획표 | 자연광 책상 위 빈 주간 플래너, 연필, 무지 메모지 | 월요일 점검부터 금요일 복기까지의 5일 흐름 | 고객 단계별 화면 |
| 소개 카드 | 정돈된 상담 테이블 위 무지 카드와 휴대폰 | 소개 카드에 들어갈 5개 정보 | 공개 소개 카드 화면 |
| 월말 복기 | 작은 계산기와 빈 차트 용지가 있는 업무 책상 | 신규 고객부터 청약까지 5개 숫자의 연결 | 개인 대시보드 |
| 연간 일정 | 계절색 탭이 있는 빈 연간 플래너 | 생일, 만기, 갱신, 다음 연락의 12개월 배치 | 일정 화면 |
| 팀장 1:1 | 마주 놓인 두 권의 노트와 펜, 사람이 없는 회의 테이블 | 면담에서 순서대로 묻는 6개 질문 | 팀장 대시보드 |

대표 이미지는 사람 얼굴, 손, 읽을 수 있는 생성 글자, 보험사 로고, 실제 증권, 과한 유리 질감과 네온 효과를 제외한다. 자연광, 사용 흔적, 조금씩 다른 재질과 구도를 사용해 다섯 장이 같은 생성 세트처럼 보이지 않게 한다. 대표 이미지는 사실 증거가 아닌 장식 이미지로만 사용하고 `alt=""`로 둔다.

설명 도식은 HTML로도 같은 정보를 바로 아래에 제공한다. 실제 화면은 `capture@inpa.local` 계열의 촬영용 데이터만 쓰고 실제 이름, 전화번호, 보험사 상품, QR, 알림 내용을 노출하지 않는다.

자산은 기존 규칙을 따른다.

- 경로: `inpa_fe/public/blog-assets/{slug}/`
- 대표 이미지: `cover.webp`
- 본문 이미지: `{role}-{8자리-content-hash}.webp`
- 권리·용도 기록: `inpa_fe/public/blog-assets/manifest.json`
- 목록 첫 화면과 상세 화면의 기존 용량 한도를 유지한다.

## 6. 신규 5편 공개 일정

| # | 공개 시각 |
|---|---|
| 21 | 2026-08-10 10:20 KST |
| 22 | 2026-08-12 14:40 KST |
| 23 | 2026-08-14 09:30 KST |
| 24 | 2026-08-18 15:10 KST |
| 25 | 2026-08-20 10:40 KST |

신규 5편은 `is_published=true`와 미래 `published_at`을 함께 저장한다. 공개 조회의 공통 조건을 `is_published=true AND published_at <= now`로 강화한다. 목록, 상세, 조회수 증가, 관련 글, 사이트맵이 이 조건을 공유해야 한다. 예약 시각 전 상세 주소는 404로 응답하고 사이트맵에도 들어가지 않는다.

## 7. 릴리스 구조와 데이터 보호

기존 `refresh_blog_content`의 검증, snapshot, transaction, 버전 마커, 롤백 흐름을 확장한다.

- release version: `2026-08-blog-expansion-v2`
- 승인 대상: 기존 20개 slug와 신규 5개 slug, 정확히 25개
- 원고 메타데이터: `publication_plan_at` 추가, KST 오프셋이 있는 ISO 8601 문자열만 허용
- 기존 20편: `published_at` 이외의 공개 콘텐츠 필드를 쓰지 않는다.
- 기존 비공개 3편: `published_at`, `is_published`, 법률 검토 필드를 쓰지 않는다.
- 신규 5편: 제목, 본문, 요약, 이미지, 카테고리, 태그, 검색 정보, 공개 예약 시각을 생성한다.
- 작성자: 신규 글의 내부 author는 관리자 계정을 사용하고, 공개 author는 기존 중앙 상수 `인파 담당자`를 유지한다.
- 같은 v2 마커와 digest의 재실행은 no-op이다.
- 같은 버전에 다른 digest가 들어오면 중단한다.
- 적용 전후 25편 snapshot을 남긴다.
- v2 적용 실패 시 transaction 전체를 롤백한다.

기존 글의 관리자 수정 내용을 지키기 위해 v2는 기존 20편의 원고 값을 DB에 다시 쓰지 않는다. 일정 적용 전 snapshot에는 기존 실제 값을 담고, 롤백도 해당 실제 값으로 복원한다.

## 8. 예약 공개 조회 규칙

공개 가능한 글의 기준은 한 곳에서 재사용한다.

```text
is_published = true
published_at is not null
published_at <= 현재 시각
법률 검토 대상이면 유효한 검토 기록이 현재 본문과 일치
```

공개 목록과 상세 ViewSet이 서로 다른 조건을 갖지 않도록 QuerySet 헬퍼 또는 manager 경계를 둔다. 사이트맵 API도 같은 공개 목록 응답을 사용하므로 미래 글이 새어 나오지 않는지 회귀 테스트한다. 관리자 목록과 미리보기에서는 미래 예약 글을 볼 수 있다.

5. Render 시작 과정의 `refresh_blog_content --apply`가 v2를 한 번 적용하고 이후에는 no-op 처리한다.
6. 운영에서 기존 17편의 날짜, 예약 전 신규 글 404, 사이트맵 제외를 확인한다.
7. 문제가 있으면 v2 before snapshot으로 복원하고 이전 배포로 되돌린다.

운영 병합과 자동 배포는 사용자가 이번 요청에서 승인했다. 배포 뒤 실제 주소와 CI 결과까지 확인하며, 다음 예약 시각이 지난 뒤 해당 글이 자동으로 노출되는지는 시간 경계 테스트와 운영 API로 다시 확인한다.

## 11. 이번 범위에서 제외

- 기존 20편 본문 재작성
- 법률 검토 대상 3편 공개
- 새 블로그 카테고리나 목록 디자인 추가
- 관리자용 범용 예약 발행 UI
- 실제 고객 사례와 후기
- 세무, 수수료, 상품 추천처럼 별도 전문가 검토가 필요한 주제
