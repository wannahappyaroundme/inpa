# 실제 고객 예약 문구·전체 링크 생성 UX 설계

**작성일:** 2026-07-27  
**상태:** 사용자 최종 승인, 상세 구현 계획 작성 완료, 구현 전

**구현 계획:** `docs/superpowers/plans/2026-07-27-release-2-booking-message-composer.md`

## 1. 문제

일정 화면의 예약 설정에는 `고객이 받는 모습(예시)`가 있지만 실제 서비스 동작이 아니다.

현재 구현:

- 고객명은 `김보장`으로 하드코딩한다.
- 링크는 `https://www.inpa.kr/b/…`로 하드코딩한다.
- 해당 영역에서 고객을 선택하거나 문구를 복사할 수 없다.
- 실제 고객명·전체 URL·복사 기능은 고객 상세의 별도 `BookingModal`에만 있다.
- `BookingModal`의 clipboard 실패는 조용히 무시한다.
- 프런트 기본 문구에는 `{소속직책}`이 있지만 백엔드 기본 문구에는 없어, 설정 preview와 실제 생성 문구가 다를 수 있다.
- 프런트 preview는 소속·직책이 비면 설계사명 앞에 공백 두 칸을 남긴다.

백엔드 `POST /customers/<id>/booking-requests/`는 이미 실제 고객명, 실제 설계사 정보, 전체 signed booking URL을 넣은 `message`를 반환한다. 문제는 생성 기능이 없어서가 아니라 설정 화면과 실사용 화면이 분리되고 가짜 preview가 서비스 UI에 남아 있는 것이다.

## 2. 목표

1. 예약 설정 화면에서 등록 고객을 검색·선택한다.
2. 현재 보이는 예약 설정을 저장한 뒤 해당 고객의 실제 예약 링크를 만든다.
3. 서버가 반환한 실제 문구와 전체 링크만 표시·복사한다.
4. `김보장`, `…`, 미치환 placeholder가 서비스 화면과 복사값에 남지 않는다.
5. 고객 상세와 일정 화면이 같은 composer를 사용해 동작이 갈라지지 않는다.
6. 복사 실패, 고객 없음, 로드 실패, 링크 생성 실패에 복구 행동을 제공한다.
7. 기본 문구의 단일 권위를 백엔드에 두고 빈 소속·직책에서도 공백이 깨지지 않게 한다.

## 3. 비목표

- 고객명 free-text만으로 고객 레코드 없는 공용 예약 링크 생성
- 카카오·문자 자동발송
- 예약 availability 계산, 수락·거절, Google Calendar 동기화 변경
- 예약 token TTL 변경
- 고객을 자동 생성하면서 링크 만들기

고객명은 free-text가 아니라 owner-scoped 등록 고객 선택이어야 한다. 예약 token, Meeting, 알림이 모두 Customer ID에 연결되기 때문이다.

## 4. 화면 구조

예약 설정 카드를 두 구역으로 나눈다.

### 4.1 예약 기본 설정

기존 설정을 유지한다.

- 내 이름
- 소속
- 직책
- 예약 안내 문구
- 업무시간
- 대면 미팅 장소
- 미팅 시간
- 앞뒤 여유
- `예약 설정 저장`

가짜 `고객이 받는 모습(예시)` 영역은 제거한다.

### 4.2 고객에게 예약 안내 보내기

실제 작업 영역을 별도로 둔다.

1. `고객 선택` 검색 combobox
2. 선택 고객의 이름·연락처 일부·영업 단계를 식별 정보로 표시
3. `고객에게 보낼 문구 만들기`
4. 실제 메시지 textarea
5. 전체 실제 URL
6. `메시지 전체 복사`
7. `링크만 복사`
8. `고객 화면 열기`

선택 전 안내:

> 고객을 선택하면 실제 예약 문구와 링크를 만들 수 있어요.

등록 고객이 없을 때:

> 고객을 먼저 추가하면 바로 예약 안내를 만들 수 있어요.

`고객 추가하기`는 기존 고객 등록 경로로 연결한다.

## 5. 데이터 흐름

```text
설계사 설정 입력
  -> 고객 검색·선택
  -> 고객에게 보낼 문구 만들기
  -> 현재 예약 설정 PATCH 저장
  -> POST /customers/<id>/booking-requests/
  -> 서버 message + booking_url
  -> 편집 가능한 실제 메시지와 전체 URL 표시
  -> 복사 또는 고객 화면 열기
```

### 5.1 저장과 생성 순서

- 설정 load 성공 전에는 저장·문구 생성을 열지 않는다.
- 사용자가 설정을 바꾼 상태에서 문구 만들기를 누르면 현재 설정을 먼저 저장한다.
- 저장 성공 뒤에만 booking request를 생성한다.
- 저장 실패 시 링크를 만들지 않으며 입력값을 보존하고 `예약 설정을 다시 저장` 행동을 제공한다.
- settings가 dirty가 아니면 불필요한 PATCH 없이 바로 booking request를 생성한다.

이 순서로 화면의 이름·소속·직책·문구와 서버가 만든 message의 불일치를 막는다.

### 5.2 고객 검색

- owner-scoped 기존 `listCustomers({search, page})`를 사용한다.
- 사용자가 입력할 때 짧은 debounce 후 검색한다.
- 빈 검색에서는 최근/우선 고객의 작은 첫 페이지를 보여준다.
- 전체 고객을 한 번에 내려받지 않는다.
- 요청 generation guard로 늦은 이전 검색 응답이 최신 결과를 덮지 않게 한다.

### 5.3 서버 응답 권위

- 프런트는 실제 메시지를 다시 조립하지 않는다.
- `BookingRequestResponse.message`와 `booking_url`을 그대로 초기 표시값으로 사용한다.
- 사용자는 메시지 textarea를 발송 전에 편집할 수 있다.
- 링크는 편집할 수 없고 전체 문자열을 줄바꿈 가능한 형태로 보여준다.
- 메시지 복사는 편집된 현재 textarea 값을 복사한다.
- 링크 복사는 서버 `booking_url` 원문을 복사한다.
- 기본 문구 렌더링의 권위는 백엔드 `templates_text.py` 한 곳에 둔다.
- 프런트의 `fillPreview`는 삭제한다. 프런트에 남는 기본 문구 문자열은 textarea의 편집 안내용 placeholder일 뿐 실제 메시지 생성에 사용하지 않는다.
- 기본 렌더는 소속·직책이 있을 때만 설계사명 앞에 한 칸을 넣고, 없을 때는 공백을 남기지 않는다.
- 사용자 저장 템플릿의 `{소속직책}` 치환 계약은 기존 호환을 유지한다.

## 6. 공용 composer

고객 상세와 일정 화면의 중복을 없애기 위해 실제 생성·편집·복사 UI를 공용 composer로 만든다.

두 사용 방식:

- 고객 상세 modal: `customerId`가 미리 정해져 있으므로 바로 링크 생성 가능
- 일정 예약 설정: 고객 검색 후 선택한 `customerId` 전달, 필요하면 `prepare()`로 현재 설정을 먼저 저장

기존 `BookingModal`은 modal shell과 닫기 동작만 담당하고 내부는 같은 composer를 사용한다.

공용 clipboard helper를 사용해 성공 여부를 실제로 확인한다. 실패 시:

> 복사하지 못했어요. 문구를 길게 눌러 직접 복사해 주세요.

메시지와 링크는 계속 선택 가능해야 한다.

## 7. 상태 설계

| 상태 | 화면과 행동 |
|---|---|
| profile loading | 설정 skeleton, 생성 비활성 |
| profile load 실패 | 기존 값처럼 보이지 않게 retry |
| customer search loading | combobox 내부 loading |
| customer search 실패 | 선택 영역 안에서 다시 불러오기 |
| 고객 미선택 | 실제 링크 생성 CTA 비활성, 선택 안내 |
| 설정 저장 중 | 단일 진행 상태, 중복 클릭 차단 |
| 링크 생성 중 | 선택·입력 유지, 중복 생성 차단 |
| 생성 실패 | 고객 선택 유지, 다시 만들기 |
| 생성 성공 | 실제 message·전체 URL·복사·열기 |
| 복사 실패 | 성공 토스트 금지, 직접 복사 안내 |
| 새 고객 선택 | 이전 고객의 message·URL 즉시 제거 |

예약 링크는 72시간 TTL이므로 오래된 composer 결과를 영구 저장하지 않는다. 다시 화면을 열거나 고객을 다시 선택하면 새 링크를 만든다.

## 8. 카피 규칙

삭제:

- `고객이 받는 모습(예시)`
- `김보장`
- `https://www.inpa.kr/b/…`

사용:

- `고객에게 예약 안내 보내기`
- `고객 선택`
- `고객에게 보낼 문구 만들기`
- `메시지 전체 복사`
- `링크만 복사`
- `고객 화면 열기`

실제 메시지에는 서버 치환 결과만 있어야 한다.

- 실제 고객명
- 저장된 소속·직책
- 저장된 설계사명
- 전체 예약 URL

## 9. 접근성·모바일

- customer combobox에 label, expanded, active descendant 등 필요한 접근성 계약을 제공한다.
- 검색 결과를 키보드로 이동·선택할 수 있다.
- 복사와 열기 버튼은 최소 44px 높이를 지킨다.
- 전체 URL은 모바일에서 가로 스크롤 대신 `overflow-wrap:anywhere`로 줄바꿈한다.
- 진행·성공 메시지는 `aria-live=polite`, 오류는 `role=alert`.
- modal은 기존 focus trap·초기 focus·닫은 뒤 focus 복귀를 검증한다.

## 10. 테스트

### 10.1 프런트

- 예약 설정에서 `김보장`, `/b/…`, `예시`가 렌더되지 않음
- 고객 검색·선택 후 정확한 customer ID로 booking request 호출
- dirty settings를 PATCH 저장한 뒤 booking request 호출 순서
- 설정 저장 실패 시 booking request 호출 0회
- 서버 message와 full URL 원문 표시
- 소속·직책이 비어도 설계사명 앞에 연속 공백이 없음
- 소속·직책이 있으면 설계사명과 자연스럽게 한 칸으로 연결
- 메시지 수정 후 수정된 값 복사
- 링크만 복사 시 full URL과 정확히 일치
- clipboard 실패 시 성공 표시 없음, 직접 복사 안내
- 고객 변경 시 이전 message·URL 제거
- 고객 없음·검색 실패·생성 실패의 다음 행동
- 고객 상세 modal과 일정 화면이 같은 composer 동작 사용

### 10.2 백엔드

- 실제 고객명 포함
- 실제 설계사명·소속·직책 치환
- full `/b/<signed-token>` URL 포함
- `{고객명}`, `{설계사명}`, `{소속직책}`, `{링크}` 미잔존
- 기본 문구에서 빈 소속·직책으로 인한 연속 공백 없음
- owner 격리와 BOOKING_ENABLED gate 유지

### 10.3 브라우저 E2E

1. 설정 화면에서 이름·소속·직책·업무시간 저장
2. 등록 고객 선택
3. 실제 문구와 full URL 생성
4. 메시지 복사 후 clipboard 내용 확인
5. 링크 열기
6. 공개 예약 화면에서 고객 마스킹명·설계사 정보·가능 시간 확인
7. 시간과 상담 방식 선택
8. 설계사 알림에서 수락
9. 일정 반영 확인

공개 `/b` 링크 열기 검증은 `2026-07-27-public-signed-route-token-normalization-design.md` 수정과 함께 수행한다.

## 11. 변경 경계와 배포

- DB migration 없음
- 기존 booking request API response 재사용
- 고객 선택과 공용 composer는 프런트 변경
- 백엔드는 기본 문구와 빈 소속·직책 공백 처리를 서버 권위로 정리하고 렌더 회귀 테스트를 보강한다.
- token 정규화 수정이 먼저 또는 같은 preview에 포함되어야 실제 URL 열기 검증이 통과한다.
- preview 검증 뒤 운영 배포는 사용자 별도 승인 후 진행한다.
