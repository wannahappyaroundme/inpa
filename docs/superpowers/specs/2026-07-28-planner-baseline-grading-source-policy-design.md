## 1. 결정 배경

현재 설계사는 `/settings/baseline`에서 전체 표준 담보의 기준 금액을 입력하고 저장할 수 있다. 그러나 운영의 `HEATMAP_GRADING_ENABLED`가 닫혀 있어 저장한 금액도 고객 한눈표의 `부족·적정·넉넉` 판정에 사용되지 않는다.

기존 `v0` 스타터 프리셋에는 공식 출처로 검증되지 않은 가설 금액이 포함되어 있다. 전역 게이트만 열면 설계사가 검토하지 않은 `v0` 값까지 판정 근거가 될 수 있으므로, 저장 가능 여부와 판정 가능 여부를 기준 출처별로 분리한다.

## 2. 확정 정책

| 기준 출처 | 의미 | 자동 판정 |
|---|---|---|
| `planner` | 설계사가 직접 입력하거나 화면에서 검토 후 저장한 기준 | 사용 |
| `preset` | 기존 `v0` 스타터 프리셋이 만든 미검증 기준 | 제외 |
| `null` | 출처가 확정되지 않은 과거 기준 | 제외 |

- 기존 `preset`·`null` 행은 삭제하거나 자동 변환하지 않는다.
- 설계사가 화면에서 `preset` 또는 출처가 비어 있는 과거 값을 검토하고 저장하면 기존 저장 계약대로 `baseline_source='planner'`, `preset_origin=null`로 전환한다.
- 전환된 값은 다음 한눈표·비교 조회부터 즉시 판정에 사용한다.
- 인파 공식 기준을 나중에 제공할 때는 검증된 별도 출처를 정의하고 별도 승인 후 판정 대상에 추가한다. 현재 `v0`를 공식 기준으로 승격하지 않는다.

## 3. 구현 구조

### 3.1 판정 대상의 단일 기준

`inpa_be/inpa/analysis/baselines.py`에 판정 가능한 출처와 필터 함수를 둔다.

- `PlannerBaseline`에는 문자열 오타를 막기 위한 출처 상수를 추가한다.
- 판정 대상은 `is_active=True`, `baseline_source='planner'`인 행으로 제한한다.
- 한눈표와 여러 증권 비교가 같은 필터 함수를 사용한다.
- `select_baseline`의 상품군·나이대·성별 우선순위는 변경하지 않는다.

### 3.2 한눈표 응답

한눈표는 다음 값을 구분한다.

- `baseline_count`: 기존 호환 필드. 출처가 있는 활성 기준 전체 수
- `applied_baseline_count`: 판정에 적용되는 `planner` 기준 수
- `unapplied_baseline_count`: 확인 전이라 판정에서 제외된 활성 기준 수
- `baseline_present`: 출처가 있는 활성 기준이 하나라도 있는지
- `grading_enabled`: 운영 판정 게이트가 열려 있는지

`mode='graded'`는 운영 게이트가 열려 있고 판정 가능한 기준이 하나 이상일 때만 반환한다. 기존 `baseline_count`의 의미는 유지하고, 화면은 새 `applied_baseline_count`를 적용 개수로 사용한다. 새 필드가 없는 이전 응답에서는 기존 `baseline_count`로 안전하게 대체한다.

### 3.3 여러 증권 비교

비교의 `mode` 판정도 한눈표와 동일한 출처 필터를 사용한다.

- `preset`만 있으면 `neutral`
- 비교 대상 담보와 일치하는 `planner` 기준이 있으면 `graded`
- 비교 금액·보험료·증감 계산은 변경하지 않는다.

### 3.4 화면 안내

- 직접 저장한 기준이 적용되면 현재의 “내 기준 N개 적용 중” 안내를 유지한다.
- 기존 추천 기준만 저장되어 있으면 “금액을 확인하고 저장하면 내 기준으로 적용돼요”라고 안내한다.
- 기준이 전혀 없으면 현재의 기준 설정 안내를 유지한다.
- `v0`, 프리셋, 게이트 같은 내부 용어는 사용자 화면에 표시하지 않는다.

기존 추천값을 금액 변경 없이 그대로 채택할 수 있도록 상세 기준 행에 `내 기준으로 사용` 동작을 제공한다.

- 기준 카탈로그 응답의 각 저장 행에 이미 존재하는 `baseline_source`를 프론트 타입과 편집 초안에 보존한다.
- `baseline_source='preset'`인 행과 출처가 비어 있는 저장 행은 “이 금액을 확인한 뒤 내 기준으로 사용하면 분석에 반영돼요”라고 안내한다.
- `내 기준으로 사용`을 누르면 초안 출처를 `planner`로 바꾸고 변경 상태로 표시한다.
- 사용자가 금액을 직접 수정한 경우에도 저장 요청은 기존처럼 해당 행을 `planner`로 전환한다.
- 배치 저장 요청 형식은 바꾸지 않는다. 서버가 저장된 행의 출처를 `planner`로 강제하는 기존 계약을 재사용한다.
- 새 빈 입력칸과 출처가 비어 있는 과거 저장 행은 `is_stored` 초안 상태로 구분한다. 저장 성공 뒤에는 이번 요청에 포함된 범위만 서버 규칙에 맞춰 동기화한다.

### 3.5 기존 미연결 행 상태

기존 미연결 행은 카탈로그 응답에서 중앙 `is_grading_eligible_baseline` 결과를 사용한다.

- `is_applied`: 활성 planner 출처이며 실제 폴백으로 사용되는 행만 `true`
- `requires_adoption`: `preset` 또는 출처 없는 과거 행처럼 중앙 출처 판정상 아직 적용할 수 없을 때 `true`이며, 활성 여부와 무관하다.
- 상태 표기: 실제 적용은 `분석에 적용 중`, 출처는 맞지만 연결이 남으면 `연결 필요`, 이전 추천값 또는 출처 없는 값은 `연결 후 금액 확인 필요`
- 연결 API는 `analysis_detail`과 이름만 바꾸며 `baseline_source`와 `preset_origin`은 보존한다. 연결 후 카탈로그를 다시 불러온 상세 행은 기존의 `내 기준으로 사용` 동작을 계속 제공한다.
- 배치 저장은 요청에 포함된 행만 `planner` 출처, `preset_origin=null`, `is_active=true`로 전환한다. 같은 화면의 요청하지 않은 범위와 다른 범위는 그대로 둔다.
- 일반 생성·수정 serializer에서 `baseline_source`, `preset_origin`, `is_active`는 모두 읽기 전용이다. FE 쓰기 타입도 이 세 필드를 노출하지 않는다.

### 3.6 운영 설정

- 코드의 기본값은 계속 `HEATMAP_GRADING_ENABLED=False`로 유지해 새 환경은 안전하게 시작한다.
- `render.yaml`의 운영 웹 서비스에 `HEATMAP_GRADING_ENABLED=True`를 명시한다.
- 작업 서버는 한눈표·비교 판정을 실행하지 않으므로 별도 설정을 추가하지 않는다.
- 운영 병합과 배포는 PM의 배포 승인 후 진행한다.

## 4. 데이터와 호환성

- DB 마이그레이션 없음
- 기존 `PlannerBaseline` 행 삭제 없음
- 기존 기준 일괄 변환 없음
- 기존 API 요청 형식 유지
- 새 응답 필드는 추가형이므로 이전 프론트와 호환
- `apply-preset` 레거시 경로는 이번 작업에서 제거하지 않지만 현재 `PRESET_DISABLED` 400을 유지한다.

## 5. 오류·빈 상태

- `preset`만 존재해도 오류로 처리하지 않는다.
- 판정 가능한 기준이 없으면 보유 금액만 표시한다.
- 기준 저장 충돌은 기존 revision 기반 409 처리를 유지한다.
- 잘못된 금액·범위 검증은 기존 serializer 규칙을 유지한다.

## 6. 검증 기준

### 백엔드

1. 운영 게이트가 열려도 `preset`만 있으면 한눈표는 `neutral`
2. `planner` 기준이 있으면 한눈표가 `graded`
3. `preset` 값을 배치 저장하면 `planner`로 전환되고 다음 조회부터 `graded`
4. `preset`과 `planner`가 함께 있어도 `planner`만 후보 선택에 사용
5. 여러 증권 비교도 같은 결과
6. 다른 설계사의 기준은 계속 격리
7. 기존 기준선·비교 회귀 테스트 통과

### 프론트엔드

1. 직접 기준 적용 중 안내
2. 이전 추천값 확인·저장 안내
3. 금액을 바꾸지 않고 `내 기준으로 사용`을 선택해도 저장 요청 생성
4. 금액을 수정한 이전 추천값도 직접 기준으로 저장
5. 기준 미설정 안내
6. 새 응답 필드가 없어도 안전한 기본값 사용
7. 카피 검사와 Next.js 빌드 통과

### 최종 검토 보완 회귀

1. 이전 추천값과 출처 없는 미연결 행은 `is_applied=false`, `requires_adoption=true`를 반환한다.
2. 연결 뒤 카탈로그 상세 행은 기존 출처를 보존하고, 명시적 저장 전에는 판정에 사용하지 않는다.
3. 금액이 바뀌지 않아도 요청된 이전 추천값·출처 없는 행은 배치 저장으로만 planner 출처로 전환한다.
4. 요청하지 않은 다른 범위의 출처·활성 상태·프리셋 표시는 바뀌지 않는다.
5. 화면은 적용 중, 연결 필요, 연결 후 금액 확인 필요를 서로 다르게 보여준다.
6. 비활성 `planner` 행은 `is_active=false`, `requires_adoption=false`로 반환하고, 화면에서 `연결 후 다시 사용 필요`와 재사용 동작을 보여준다.
7. 재사용은 기존 batch 요청 형식을 유지하며, 저장 성공 뒤 요청 범위만 활성 상태로 바꾼다.

### 운영

1. Render 배포 성공
2. `/healthz/` 200
3. 기준 입력·저장 API 정상
4. 실제 테스트 계정에서 저장 전 `neutral`, 저장 후 `graded`
5. 한눈표와 여러 증권 비교의 판정 모드 일치

운영 검증은 별도의 테스트 계정과 비식별 고객 자료로 수행한다. 검증 후 테스트 기준은 삭제하지 않고 비활성화해 판정 이력과 감사 가능성을 보존한다.
