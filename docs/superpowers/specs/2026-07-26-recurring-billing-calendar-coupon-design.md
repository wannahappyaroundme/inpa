# 달력 개월 쿠폰·정기결제 확정 설계

- 일자: 2026-07-26
- 상태: 사용자 상세 설계 승인, 구현 전 문서 검토
- 채택안: **2안, 결제 원장과 이용 권한 분리**
- 선행 자료:
  - `2026-07-26-recurring-billing-coupon-council.md`
  - `2026-07-15-billing-annual-first-paid-bonus-autopay.md`

## 1. 목표

1. 관리자가 1~3개월 일반 쿠폰을 발행하고 사용기한과 사용 가능 인원을 정한다.
2. 회원은 카드를 먼저 등록해야 쿠폰을 사용할 수 있다.
3. 무료 기간은 30일 단위가 아니라 한국 달력 날짜 기준으로 계산한다.
4. 무료 기간 뒤 첫 유료 결제 전에 날짜·금액·해지 조건을 다시 확인받는다.
5. 승인 성공, 명시적 실패, 결과 미확정을 구분해 중복 결제와 잘못된 이용 중단을 막는다.
6. 유료 종료 후 무료 요금제로 바뀌면 사건별 최초 1회 안내하고, 기존 고객 기록은 계속 보존한다.
7. 비개발자인 운영자가 쿠폰·동의·결제·취소·미확정 건을 관리자 화면에서 처리할 수 있게 한다.

## 2. 범위

### 이번 범위

- 월 정기결제
- 1~3개월 카드 등록형 일반 쿠폰
- KICC 빌키 발급·삭제, 정기 승인, 거래 조회, 전체 취소
- 첫 유료 결제 재확인
- 무료 전환 안내
- 관리자 쿠폰·결제 운영 화면
- 결제·쿠폰·안내·감사 이벤트 계측

### 이번 범위가 아닌 것

- 연간 자동 결제 전환
- 부분 환불 자동 계산
- 가족·팀 단위 공동 결제
- 쿠폰 양도·선물
- 원본 녹음 장기 보관
- 결제 여부를 이유로 기존 고객 데이터를 잠그는 기능

기존 연간 수동 이용권 경로는 호환을 유지하고, 월 자동 결제가 안정화된 뒤 별도로 전환한다.

## 3. 제품 원칙: 고객 데이터는 축적 가치이지 잠금 수단이 아니다

설계사가 쌓은 고객, 여러 메모, AI 요약, 일정, 후속 행동은 장기 고객 관리 이력이다.

- 유료 요금제가 끝나도 기존 고객·메모·AI 요약은 삭제하지 않는다.
- 무료 전환 뒤에도 기존 기록을 열람하고 직접 수정할 수 있다.
- 새 녹음, 새 AI 요약, 자동 후속 관리 등 새로 비용이 발생하는 기능은 현재 요금제 한도를 적용한다.
- 원본 녹음은 요금제와 무관하게 생성 후 7일 안에 삭제한다.
- 녹음 하나당 AI 요약은 성공 기준 1회만 생성하고, 이후에는 사용자가 텍스트를 직접 수정한다.
- 분석·운영 로그에는 메모·요약 원문을 넣지 않고 건수, 상태, 식별자만 기록한다.

장기 잔존은 데이터 반출 방해가 아니라 날짜별 상담 맥락, 검색 가능한 이력, 후속 행동 연결, 새 업무 자동화에서 만든다.

## 4. 사용자 흐름

### 4.1 쿠폰 등록과 무료 시작

1. 회원이 쿠폰 코드를 입력한다.
2. 서버가 쿠폰 종류, 사용기한, 남은 수량, 회원 사용 이력을 확인한다.
3. 유효하면 15분 동안 해당 회원에게 쿠폰 사용 자리를 점유한다.
4. 회원에게 다음 내용을 보여준다.
   - 무료 이용 종료일
   - 첫 결제 예정일
   - 첫 결제 예정 금액(VAT 포함)
   - 언제든 다음 결제를 멈추는 경로와 적용 시점
5. 회원이 카드 등록과 무료 시작 동의에 체크한다.
6. KICC 창에서 카드 등록을 완료한다.
7. 서버가 빌키 발급 결과를 검증한 뒤 한 트랜잭션에서 쿠폰 사용, 결제 약정, 무료 이용 권한을 확정한다.
8. 완료 화면과 요금제 화면에 무료 종료일과 다음 단계를 표시한다.

점유가 만료되거나 카드 등록이 끝나지 않으면 쿠폰은 사용 처리하지 않는다. 늦게 도착한 카드 등록 성공 콜백은 이용권을 만들지 않고 빌키를 폐기한다.

### 4.2 첫 유료 결제 재확인

카드 등록 시의 무료 시작 동의와 첫 유료 결제 재확인은 별도 사건으로 저장한다.

- 1개월 쿠폰: 첫 결제 7일 전부터 결제일 직전 23:59(KST)까지 재확인 가능
- 2~3개월 쿠폰: 첫 결제 30일 전부터 결제일 직전 23:59(KST)까지 재확인 가능
- 화면에 VAT 포함 금액, 결제일, 카드 표시 정보, 해지 경로, 해지 효과를 고정 스냅샷으로 보여준다.
- 회원이 확인을 마치면 동의 문구 버전, 표시값, 시각, IP의 비식별 네트워크 정보, 사용자 에이전트를 감사용으로 저장한다.
- 결제일 직전 23:59(KST)까지 재확인하지 않으면 승인 요청을 보내지 않고 무료 요금제로 전환하며 빌키를 폐기한다.

재확인 알림 채널은 앱 알림과 이메일을 기본으로 한다. 알림 발송 실패는 결제 상태를 바꾸지 않으며 운영 화면에 실패 상태만 남긴다.

### 4.3 정상 정기결제

1. KST 결제일 00:00에 결제 주기가 도래하며, 정해진 배치 시각에 결제 주문을 만든다.
2. 내부 영구 주기 키로 같은 회원·같은 주기의 주문이 이미 있는지 확인한다.
3. KICC에 한 번 승인 요청한다.
4. 승인 응답의 상점 ID, 주문번호, 금액, 무결성 값을 검증한다.
5. 승인 성공과 유료 이용권 연장을 하나의 서비스 트랜잭션으로 확정한다.
6. 다음 결제일을 최초 기준일로 다시 계산한다.
7. 영수·결제 안내 이벤트를 생성한다.

00:00부터 승인 결과 확정 전까지는 짧은 `renewal_processing` 유예 상태로 기존 이용 권한을 유지한다. 승인되면 새 이용기간은 결제일 00:00부터 시작한 것으로 기록해 화면상 이용 중단을 만들지 않는다. 거절되면 거절 확정 시각에 무료로 전환하고, 결과를 알 수 없으면 아래의 24시간 미확정 규칙을 적용한다.

### 4.4 결제 실패

카드 거절처럼 실패가 확정된 경우:

- 같은 주기에서 자동 재승인하지 않는다.
- 빌키를 폐기하고 무료 요금제로 전환한다.
- 기존 고객 기록은 유지한다.
- 회원에게 카드 재등록과 직접 결제 경로를 안내한다.
- 나중에 직접 결제에 성공한 실제 날짜를 새 기준일로 정한다.

### 4.5 결제 결과 미확정

네트워크 시간초과나 응답 유실처럼 승인 여부를 모르는 경우:

- 재승인하지 않는다.
- 주문을 `unknown`으로 두고 KICC 거래 조회로만 상태를 확정한다.
- 회원의 이용을 최대 24시간 임시 유지한다.
- 5분과 30분에 운영 알림을 보낸다.
- 24시간 안에 실패가 확인되면 무료로 전환한다.
- 24시간 뒤에도 확인할 수 없으면 임시 이용을 종료하고 운영 건으로 남긴다.
- 나중에 승인 성공이 발견되면 짧아진 이용권을 조용히 되살리지 않고 전액 취소 또는 운영 검토로 처리한다.

## 5. 달력 날짜 계산

### 5.1 기준

- 저장 시각은 UTC, 결제 날짜 계산과 화면 표시는 `Asia/Seoul`을 사용한다.
- 이용 구간은 `[시작일 00:00, 다음 결제일 00:00)`의 반개방 구간이다.
- 화면에는 다음 결제일의 전날을 “이용 가능일”로 표시한다.
- 최초 쿠폰 활성화 날짜의 일자를 `billing_anchor_day`로 영구 보존한다.
- 각 달에 그 일자가 없으면 해당 달의 마지막 날로만 보정한다. 다음 달에는 최초 기준일을 다시 사용한다.

### 5.2 예시

| 시작일 | 무료 개월 | 무료 이용 가능일 | 첫 결제일 | 다음 결제일 |
|---|---:|---|---|---|
| 2027-01-05 | 1개월 | 2027-02-04까지 | 2027-02-05 | 2027-03-05 |
| 2027-02-08 | 1개월 | 2027-03-07까지 | 2027-03-08 | 2027-04-08 |
| 2027-01-31 | 1개월 | 2027-02-27까지 | 2027-02-28 | 2027-03-31 |
| 2028-01-31 | 1개월 | 2028-02-28까지 | 2028-02-29 | 2028-03-31 |

월말 보정된 2월 28일이나 29일을 새 기준일로 덮어쓰지 않는다.

### 5.3 새 기준일이 생기는 경우

- 최초 쿠폰 활성화
- 무료 상태에서 회원이 직접 결제에 성공
- 기존 약정을 끝낸 뒤 새 카드로 새 약정을 시작

단순 카드 교체, 관리자 메모 수정, 결제 결과 조회는 기준일을 바꾸지 않는다.

## 6. 쿠폰 규칙

### 6.1 종류

기존 쿠폰은 호환을 위해 다음 두 종류로 분리한다.

- `legacy_grant`: 기존 일수형 이용권 지급
- `recurring_trial`: 카드 등록형 달력 개월 무료 체험

새 일반 쿠폰은 `recurring_trial`만 사용하며 `duration_months`는 1, 2, 3 중 하나다.

### 6.2 관리자가 정하는 값

- 쿠폰 이름과 내부 설명
- 코드 또는 코드 생성 규칙
- 적용 요금제
- 무료 개월 수(1~3)
- 코드 사용 마감일시
- 최대 사용 회원 수
- 활성 여부

발급 후 사용된 쿠폰의 기간·요금제는 소급 변경하지 않는다. 쿠폰 사용 시 당시 정책을 `CouponClaim`에 스냅샷으로 저장한다.

### 6.3 사용 제한

- 한 회원은 같은 쿠폰을 한 번만 사용한다.
- 전체 사용 수량은 DB 잠금과 조건부 갱신으로 보호한다.
- 쿠폰 점유는 15분이며 만료 후 자동 해제한다.
- 계정 간 악용 추적을 위해 전화번호, 이메일, 카드 지문을 새로 결합하지 않는다.
- 관리자는 쿠폰별 사용 내역과 취소 사유를 볼 수 있다.

## 7. 데이터 구조

기존 `Subscription`은 현재 이용 권한의 투영으로 유지하고 금전 거래의 원장으로 사용하지 않는다.

### 7.1 신규·확장 모델

| 모델 | 역할 | 주요 값 |
|---|---|---|
| `Coupon` 확장 | 쿠폰 정책 | `coupon_kind`, `duration_months`, `redeem_by`, `max_redemptions` |
| `CouponClaim` | 점유·사용 확정 | 회원, 쿠폰, 상태, 만료시각, 정책 스냅샷 |
| `BillingAgreement` | 정기결제 약정 | 회원, 요금제, 기준일, 상태, 다음 결제일 |
| `PaymentMethodToken` | 결제수단 권한 | 암호화 빌키, 카드 표시값, 상태, 폐기시각 |
| `RecurringPaymentConsent` | 무료 시작·첫 결제 재확인 증거 | 종류, 문구 버전, 표시 스냅샷, 동의시각 |
| `PaymentOrder` | 결제 주기별 영구 주문 | 약정, 주기 번호, 금액, 상태 |
| `PaymentAttempt` | 외부 요청·응답 이력 | 제공사 거래 ID, 결과 종류, 오류 코드 |
| `WebhookInbox` | 웹훅 원문 대신 검증 가능한 수신 봉투 | 이벤트 ID, 해시, 검증 상태, 처리 상태 |
| `BillingNoticeEvent` | 안내 1회와 발송 상태 | 사건 키, 채널, 표시·확인시각 |

### 7.2 주요 제약

- `CouponClaim(coupon, user)` 사용 확정 유일성
- `PaymentOrder(agreement, cycle_sequence)` 영구 유일성
- 제공사 거래 ID가 있으면 전역 유일성
- 같은 결제 사건의 무료 전환 안내는 `BillingNoticeEvent(user, event_key, notice_type)` 유일성
- 활성 약정당 활성 빌키 하나

KICC의 요청 멱등 보장 기간에만 의존하지 않고 인파 DB의 영구 유일성으로 중복 결제를 막는다.

### 7.3 상태

- `BillingAgreement`: `trialing`, `renewal_processing`, `active`, `past_due_unknown`, `canceled`, `free`
- `PaymentOrder`: `created`, `submitted`, `approved`, `declined`, `unknown`, `canceled`, `refunded`
- `CouponClaim`: `held`, `redeemed`, `released`, `expired`
- `PaymentMethodToken`: `active`, `revocation_pending`, `revoked`

상태 전이는 서비스 계층 한 곳에서 수행하며, 모델을 직접 수정하는 관리자 기능은 제공하지 않는다.

## 8. 무료 전환 안내

### 8.1 발생 사건

- 첫 결제 재확인 미완료
- 카드 승인 실패
- 사용자가 다음 결제 중단
- 유료 이용기간 정상 종료
- 운영자 취소

각 사건은 고유 `event_key`를 가진다. 같은 사건의 큰 팝업은 계정 전체에서 한 번만 보여준다.

### 8.2 여러 기기에서 1회 보장

1. 화면이 안내 임대를 요청한다.
2. 서버가 짧은 임대를 원자적으로 한 기기에 준다.
3. 화면이 실제로 그린 뒤 `rendered_at`을 확인한다.
4. 브라우저가 닫혀 그리지 못하면 임대가 만료되어 다른 기기에서 다시 시도한다.
5. 팝업을 닫은 뒤에도 요금제 화면의 작은 안내에서 상태를 다시 확인할 수 있다.

팝업의 핵심 문구:

- 현재 무료 요금제로 이용 중
- 기존 고객과 메모는 그대로 보관
- 새 녹음·AI 요약은 무료 한도 적용
- 카드를 등록하고 다시 시작하는 버튼

## 9. 해지·환불

### 9.1 다음 결제 중단

- 요청 즉시 다음 결제를 멈춘다.
- 빌키 폐기를 요청한다.
- 이미 확보한 이용기간 마지막 날까지 현재 요금제를 유지한다.
- 이후 무료로 전환한다.

### 9.2 자동 전액 취소 대상

- 중복 승인
- 승인 금액 불일치
- 승인됐지만 유료 이용 권한을 주지 못했고 안전하게 복구할 수 없는 경우
- 늦은 승인 성공으로 이미 무료 전환된 미확정 주문

### 9.3 별도 운영 심사

법정 청약철회, 서비스 장애, 일부 환불은 요청 접수와 관리자 처리 이력을 남기는 별도 흐름으로 둔다. 정확한 환불 기한과 공제 문구는 운영 개방 전 법적 문구 검토로 확정한다.

## 10. 관리자 화면

비개발자가 다음을 처리할 수 있어야 한다.

### 쿠폰

- 생성·수정·비활성화
- 1~3개월, 사용기한, 최대 인원 설정
- 점유·사용·해제 내역 확인
- 회원별 적용 결과 확인

### 구독·결제

- 회원의 현재 이용 권한과 다음 결제일
- 무료 시작·첫 결제 재확인 증거
- 마스킹된 카드 표시 정보
- 주문·승인·실패·미확정·취소 이력
- 미확정 거래 조회 재실행
- 빌키 폐기 재시도
- 전액 취소·환불 사유와 결과

### 운영 대기열

- 5분·30분 이상 미확정
- 빌키 폐기 실패
- 승인 성공 후 권한 불일치
- 웹훅 검증 실패
- 안내 발송 실패

관리자 목록에는 고객 메모·AI 요약·녹음 원문을 표시하지 않는다.

## 11. 보안·개인정보

- 카드번호와 CVC는 인파 서버를 통과하거나 저장하지 않는다.
- KICC 빌키는 서버에서 애플리케이션 수준으로 암호화하고 키는 운영 비밀 저장소에 둔다.
- 로그에는 빌키, 카드번호, 동의 원문, 고객 메모를 남기지 않는다.
- 웹훅과 조회 응답은 상점 ID, 주문번호, 금액, 서명·무결성 값을 검증한다.
- 관리자 결제 작업은 관리자 권한, 재인증, 감사 로그를 요구한다.
- 결제·동의·계약 기록은 법정 보존기간 정책에 맞춰 분리 보관한다.
- 빌키는 활성 결제 권한이 끝나면 폐기하고 폐기 실패를 재시도한다.

초기 보존 기준:

- 계약·결제·동의 증거: 5년
- 소비자 분쟁 처리 기록: 3년
- 표시·광고 관련 기록: 6개월
- 빌키: 활성 결제 권한 기간까지만

운영 개방 전 최신 법령·PG 계약 기준으로 다시 확인한다.

## 12. 기능 게이트와 운영 개방

기본값이 닫힌 세 게이트를 둔다.

1. `BILLING_CARD_REGISTRATION_ENABLED`
2. `BILLING_RECURRING_CHARGE_ENABLED`
3. `BILLING_WEBHOOK_RECONCILIATION_ENABLED`

의존 규칙:

- 카드 등록이 닫히면 새 쿠폰 체험을 시작할 수 없다.
- 정기 승인이 닫혀도 기존 약정 조회, 빌키 폐기, 취소, 미확정 대사는 계속 동작해야 한다.
- 웹훅 게이트가 닫혀도 거래 조회 기반 복구 경로는 유지한다.

현재 `FREE_TIER_UNLIMITED=True` 상태에서는 실제 유료 전환을 열지 않는다. 무료 요금제의 새 녹음·AI 요약·기타 사용량 정책을 먼저 확정하고 화면·API에 동일하게 적용한다.

## 13. 분석 지표

원문 없이 다음 사건만 기록한다.

- 쿠폰 보기 → 코드 확인 → 카드 등록 시작 → 카드 등록 완료 → 무료 시작
- 재확인 화면 보기 → 재확인 완료
- 첫 유료 승인 성공·거절·미확정
- 1·2·3개월별 첫 유료 전환율
- 무료 전환 안내 노출·다시 시작
- 결제 후 30·60·90일 잔존
- 고객당 메모 수, AI 요약 수, 최근 30일 새 상담 기록 수

메모·요약 내용, 고객 이름, 전화번호, 녹음 내용은 분석 이벤트에 포함하지 않는다.

## 14. 마이그레이션

1. 기존 쿠폰 행을 `legacy_grant`로 채운다.
2. 이미 사용된 기존 쿠폰 혜택은 그대로 보존한다.
3. 아직 사용되지 않은 기존 일수형 코드는 운영 목록으로 내보내 확인 후 비활성화하거나 새 코드로 재발행한다. 자동으로 달력 개월 쿠폰으로 바꾸지 않는다.
4. 기존 활성 `Subscription`은 이용 권한으로 유지하고 결제 원장을 거꾸로 추정해 만들지 않는다.
5. 새 결제 약정은 새 흐름에서만 생성한다.
6. 마이그레이션은 PostgreSQL에서 동시성·유일성 제약까지 검증한다.

## 15. 오류·빈 상태·모바일 기준

- 카드 등록 취소: 쿠폰 점유 남은 시간을 보여주고 다시 시작할 수 있게 한다.
- 사용기한 종료: 사용할 수 있는 다른 혜택이나 요금제 확인 경로를 안내한다.
- 수량 소진: 현재 요금제와 직접 결제 경로를 보여준다.
- 결제 미확정: 이용이 임시 유지 중임을 알리고 재결제를 유도하지 않는다.
- 결제 실패: 새 카드 등록 버튼과 기존 데이터 보존 안내를 함께 보여준다.
- 관리자 빈 상태: “처리할 결제 건이 없습니다”처럼 정상 상태를 설명한다.
- 모든 주요 흐름은 360px 모바일 폭, 키보드 탐색, 로딩·중복 클릭 방지를 포함한다.

사용자 화면에는 `빌키`, `멱등성`, `대사`, `컴플라이언스` 같은 운영 용어를 노출하지 않는다.

## 17. 운영 개방 조건

다음이 모두 완료되기 전에는 운영 자동 결제를 켜지 않는다.

- KICC 상점 심사와 운영 자격 증명 등록
- 샌드박스 전체 흐름 통과
- 첫 유료 결제 재확인 문구와 환불 정책 확정
- PostgreSQL 동시성 시험 통과
- 스케줄러 중단·재시작 복구 시험
- 승인·취소·정산 실거래 확인
- 관리자 운영 지침과 CS 답변 준비
- Sentry·결제 미확정·예상 이벤트 무발생 알림 준비
- 무료 요금제 한도와 유료 가치가 실제 API·화면에 일치

운영 배포는 코드 병합과 별개의 사용자 승인 단계로 진행한다.

## 18. 구현 분리

두 기능은 같은 고객 가치 전략을 공유하지만 한 브랜치에서 섞지 않는다.

- 트랙 A, 상담 기록: 다중 메모 완료 → 원본 녹음 7일 보관 → 녹음당 AI 요약 성공 1회
- 트랙 B, 결제: 결제 원장 → 카드 등록형 1~3개월 쿠폰 → 재확인형 자동 결제

상담 기록 기능을 먼저 안정화해 실제로 쌓이는 고객 이력의 가치를 만들고, 결제 기능은 운영 게이트를 닫은 상태로 병행 개발할 수 있다. 각 트랙은 별도 커밋, 별도 검증, 별도 운영 개방 승인을 가진다.
